# Бэкенд «Тверь рядом» на FastAPI

Переписанный API сайта экскурсий. Лежит отдельно от `apps/api` и ни на что
не влияет: **прежний бэкенд на Cloudflare Workers продолжает обслуживать
рабочий сайт**, пока этот не будет готов и не получит домен.

## Чем отличается от прежнего

| | Было (Workers) | Стало |
|---|---|---|
| Язык и каркас | TypeScript, Hono | Python 3.12, FastAPI |
| База | D1 (SQLite), Drizzle | PostgreSQL, SQLAlchemy 2.0 + Alembic |
| Фоновые задачи | Cron Triggers | APScheduler внутри процесса |
| Фотографии | R2 через привязку, ресайз в браузере | тот же R2, ресайз на сервере |
| Развёртывание | `wrangler deploy` | Docker Compose на VPS |

Пароли **не меняются**: хеши считались PBKDF2-SHA256 на 100 000 итераций,
и Python даёт тот же результат байт в байт. База переезжает как есть,
никому не нужно заводить пароль заново.

Формат ответов сохранён дословно — `{"success": …, "data": …}` и
`{"success": false, "error": {"code", "message"}}`. Сайт, админка и боты
читают `code`, а не HTTP-статус, и смены языка не заметят.

## Устройство

```
app/
  core/          настройки, база, безопасность, ошибки, единица работы
  domain/
    models/      таблицы (SQLAlchemy)
    schemas/     что принимаем и отдаём (Pydantic)
  repositories/  запросы к одной таблице
  services/      бизнес-логика
  api/           маршруты и зависимости
```

Слои разделены намеренно. Маршрут разбирает запрос и отдаёт ответ, сервис
решает, что делать, репозиторий знает, как спросить у базы. В прежней
версии запросы Drizzle лежали прямо в обработчиках, и одно и то же условие
(«опубликованная экскурсия по слагу») встречалось в четырёх местах и
постепенно расходилось.

Транзакцией распоряжается `UnitOfWork`: сервис делает свою работу, а
маршрут фиксирует её одним `commit`. На D1 интерактивных транзакций не
было, и создание брони шло двумя отдельными запросами — между ними воркер
мог упасть и оставить занятое место без брони.

## Запуск

```bash
python -m venv .venv
.venv/Scripts/pip install -e ".[dev]"     # Linux: .venv/bin/pip
cp .env.example .env
```

Целиком, вместе с базой:

```bash
docker compose up --build
```

Только приложение (база должна быть поднята отдельно):

```bash
alembic upgrade head
uvicorn app.main:app --reload
```

Документация — на `/docs`, в продакшене она отключена.

## Тесты

```bash
.venv/Scripts/python -m pytest
```

База в тестах — SQLite в памяти, как было на Vitest: прогон занимает
секунды и не требует поднятого Postgres. Схема строится из тех же моделей.

## Совместимость формата

Состав полей ответа сверяется не на глаз: публичные схемы — по выдаче
работающего API, админские — по типам из `apps/admin/src/lib/types.ts`.
На момент переноса админки все десять её схем совпадают поле в поле.

## Где поведение намеренно отличается

Переносилось почти дословно, но в трёх местах прежнее поведение выглядит
ошибкой, и оно исправлено:

- **поиск пользователя по почте** стал нечувствителен к регистру. Раньше
  `Elena@` и `elena@` заводили двух разных людей;
- **лента отзывов на главной** больше не показывает отзывы о снятых
  с публикации экскурсиях: такая карточка вела на несуществующую страницу;
- **ответ на неизвестный адрес при входе** теперь занимает столько же
  времени, сколько на известный. Раньше по скорости можно было перебирать
  зарегистрированные адреса.

## Предохранители гостевых точек

Вход, регистрация, форма обратной связи, отзывы и гостевые брони
ограничены по частоте запросов — числа те же, что были на Workers.
Вошедшего ограничение не касается: его держат сессия и возможность её
отозвать, а предел по адресу бил бы по всем из одной сети.

Рядом — проверка «я не робот» (Turnstile). Пока секрет не задан, она
пропускает всех: так форма работает и до подключения виджета. Недоступная
проверка считается отказом, иначе её можно было бы обойти, уронив связь
с Cloudflare.

## Про несколько процессов

Фоновые задачи крутятся внутри процесса приложения. Если запустить
несколько рабочих процессов `uvicorn`, планировщик поднимется в каждом.
Очередь доставки к этому готова — задачи берутся с блокировкой строки
и пропуском занятых, так что одно сообщение не уйдёт дважды.

Счётчики частоты запросов живут в памяти процесса, поэтому при нескольких
рабочих процессах предел окажется во столько же раз мягче. Для сайта
экскурсовода это приемлемо; если понадобится точный общий счётчик,
достаточно подставить другую реализацию `RateLimiter`.
